# Auditoría SEO — The Builders Camp

**Fecha:** 15 de octubre de 2026  
**Sitio:** https://www.thebuilderscamp.com/  
**Alcance:** revisión técnica, indexación, SEO on-page, contenido, datos estructurados, rendimiento potencial y calidad del proyecto Next.js.

## Resumen ejecutivo

El sitio tiene una base SEO sana y no presenta bloqueos críticos de rastreo o indexación. La home, `/apply`, `robots.txt` y `sitemap.xml` responden correctamente; las variantes HTTP y sin `www` redirigen a la URL canónica; existe HSTS; la home declara un canonical coherente, permite indexación y contiene datos estructurados renderizados para `WebSite`, `Organization` y `Event`.

La principal limitación no es técnica sino competitiva: casi toda la propuesta vive en una sola landing. Esto permite posicionar la marca, pero entrega pocas páginas y poca profundidad temática para búsquedas como “bootcamp para jóvenes Chile”, “emprendimiento para estudiantes”, “programas de liderazgo juvenil”, “becas para estudiantes de enseñanza media” o “habilidades del futuro para jóvenes”.

Los riesgos de mayor impacto son:

1. Imágenes PNG excesivamente pesadas y varios recursos visuales cargados sin optimización automática.
2. Toda la home es un componente cliente con GSAP y numerosas animaciones, lo que aumenta JavaScript, hidratación y riesgo para LCP/INP.
3. Arquitectura de contenido demasiado pequeña: solo home y formulario indexables.
4. Navegación del footer simulada con texto no enlazado y ausencia de páginas de confianza/legales.
5. H1 atractivo para marca, pero poco explícito para la intención de búsqueda principal.

**Estado general:** saludable para indexación; mejorable en rendimiento, arquitectura de contenidos y señales de confianza.

## Hallazgos técnicos

### 1. Imágenes demasiado pesadas

- **Impacto:** Alto.
- **Evidencia:** `faq-balloon.png` pesa 1,91 MB; `footer-journey.png`, 1,90 MB; `application-airship.png`, 1,64 MB; `application-airship-transparent.png`, 1,60 MB; `sky-transition.png`, 1,43 MB; `program-plane.png`, 558 KB. Los PNG grandes suman más de 9 MB en el repositorio.
- **Problema:** `sky-transition.png` y `footer-journey.png` se usan como fondos CSS, por lo que no reciben optimización responsive de `next/image`. `faq-balloon.png` y `program-plane.png` usan `<img>` sin `loading="lazy"`, y el linter advierte siete usos de `<img>`.
- **Recomendación:** convertir recursos fotográficos/degradados a AVIF o WebP; exportar cada ilustración al tamaño máximo real de renderizado; usar `next/image` con `sizes`, `quality` y lazy loading para imágenes de contenido; mantener SVG para logos; medir después en móvil.
- **Prioridad:** P1.

### 2. Exceso de JavaScript e hidratación en la home

- **Impacto:** Alto.
- **Evidencia:** `app/page.tsx` comienza con `"use client"` y concentra todo el contenido estático, GSAP, ScrollTrigger, estado de FAQ y animaciones en un único componente cliente.
- **Problema:** aunque Next.js prerenderiza la ruta, el navegador debe descargar e hidratar una landing grande. Esto puede empeorar INP, uso de CPU y experiencia en móviles de gama media.
- **Recomendación:** convertir la página principal en Server Component; aislar FAQ, programa desplegable y animaciones en pequeños Client Components; cargar animaciones no críticas de forma diferida; respetar `prefers-reduced-motion` en todas las animaciones, no solo en algunas.
- **Prioridad:** P1.

### 3. LCP basado en una imagen de fondo CSS

- **Impacto:** Medio-Alto.
- **Evidencia:** la imagen principal `/hero/hero.webp` se precarga manualmente, pero se pinta mediante `background-image`.
- **Problema:** una imagen CSS no aprovecha `srcset`/`sizes` ni la selección responsive de `next/image`. El recurso actual pesa solo 115 KB, lo cual es positivo, pero se entrega igual a todos los dispositivos.
- **Recomendación:** evaluar un `<Image fill priority fetchPriority="high">` detrás del contenido, con `sizes="100vw"`, manteniendo el gradiente como capa CSS. Verificar que sea el elemento LCP real.
- **Prioridad:** P2.

### 4. `robots.txt`, sitemap, canonicals y redirecciones están correctos

- **Impacto:** Positivo.
- **Evidencia:** `/`, `/apply`, `/robots.txt` y `/sitemap.xml` responden 200. `http://` redirige a HTTPS y el dominio sin `www` redirige a `www` mediante 308. La home declara `https://www.thebuilderscamp.com` como canonical y `index, follow`. HSTS está activo con `max-age=63072000`.
- **Recomendación:** mantener esta configuración y registrar el sitemap en Google Search Console y Bing Webmaster Tools.
- **Prioridad:** Mantener.

### 5. Fechas del sitemap generadas con `new Date()`

- **Impacto:** Bajo-Medio.
- **Evidencia:** `app/sitemap.ts` asigna `lastModified: new Date()` a ambas URLs.
- **Problema:** cada despliegue cambia `lastmod` aunque el contenido no haya cambiado. Esto reduce la calidad de la señal de frescura.
- **Recomendación:** usar la fecha real de última modificación de cada página o eliminar `lastModified` si no se puede mantener con precisión. La prioridad `0.9` de `/apply` también es demasiado cercana a la home; Google normalmente ignora `priority`, pero una configuración más realista sería `0.6–0.7`.
- **Prioridad:** P3.

### 6. Idioma inconsistente

- **Impacto:** Bajo.
- **Evidencia:** el HTML usa `lang="es"`, mientras Open Graph y JSON-LD especifican `es_CL`/`es-CL`.
- **Recomendación:** usar `<html lang="es-CL">` para coherencia regional.
- **Prioridad:** P3.

### 7. Datos estructurados presentes y renderizados

- **Impacto:** Positivo con mejoras posibles.
- **Evidencia:** el DOM publicado contiene JSON-LD para `WebSite`, `Organization` y `Event`; el evento incluye nombre, fechas, modalidad presencial, lugar, organizador, precio, moneda, disponibilidad y URL de postulación.
- **Mejoras:** añadir dirección más completa (`streetAddress` y, si corresponde, `postalCode`); definir imágenes de evento en varios formatos/aspectos; añadir `validFrom` a la oferta cuando se conozca; mover el schema específico del evento a la home para no repetirlo automáticamente en `/apply`; validar en Google Rich Results Test después de cada cambio.
- **Prioridad:** P2.

### 8. Compilación correcta, lint con errores

- **Impacto:** Medio para mantenibilidad; indirecto para SEO.
- **Evidencia:** `npm run build` compila y genera estáticamente `/`, `/apply`, `/robots.txt` y `/sitemap.xml`. `npm run lint` devuelve 3 errores y 8 advertencias: dos usos de `any`, una entidad sin escapar, una variable sin usar y siete advertencias por `<img>`.
- **Recomendación:** corregir el lint y exigir `npm run lint && npm run build` en CI antes de desplegar.
- **Prioridad:** P2.

## Hallazgos on-page

### 9. Title y description bien dimensionados

- **Impacto:** Positivo.
- **Evidencia home:** title de 55 caracteres y meta description de 149 caracteres, únicos y alineados con “habilidades del futuro” y “jóvenes”.
- **Evidencia `/apply`:** title de 56 caracteres y description de 137 caracteres, únicos y específicos.
- **Recomendación:** mantenerlos y probar una variante más orientada a intención geográfica: “Bootcamp para Jóvenes en Chile | The Builders Camp”. No cambiar sin revisar impresiones/CTR en Search Console.
- **Prioridad:** P3 / experimento.

### 10. H1 poco descriptivo para búsquedas genéricas

- **Impacto:** Medio-Alto.
- **Evidencia:** el H1 es “Conviértete en el Builder del Mañana”. “Bootcamp”, “jóvenes”, “Chile” y “habilidades del futuro” aparecen cerca, pero no en el encabezado principal.
- **Recomendación:** mantener la fuerza creativa e incorporar contexto: “Conviértete en el Builder del Mañana: bootcamp para jóvenes” o añadir una línea semántica visible que complete con “Bootcamp de habilidades del futuro para estudiantes de enseñanza media”.
- **Prioridad:** P1.

### 11. Footer con enlaces aparentes que no son enlaces

- **Impacto:** Medio.
- **Evidencia:** “Currículo”, “Admisiones”, “Becas”, “Directorio Alumni”, “Partner Schools”, “Blog”, “Podcast”, “Recursos Abiertos”, etc. se renderizan como `<span>`.
- **Problema:** no distribuyen autoridad interna, no crean rutas rastreables y pueden frustrar al usuario porque visualmente parecen navegación.
- **Recomendación:** convertir únicamente los destinos reales en enlaces; eliminar temporalmente los que no existan. Priorizar páginas de Programa, Admisiones/Requisitos y Becas.
- **Prioridad:** P1.

### 12. Texto alternativo mejorable

- **Impacto:** Bajo.
- **Evidencia:** el logo del footer usa `alt="Logo"`; “Hiveyoung Logo” es genérico/inconsistente. Las ilustraciones decorativas tienen `alt=""`, lo cual es correcto.
- **Recomendación:** usar “The Builders Camp” y “HiveYoung, organizador de The Builders Camp”. Mantener alt vacío en imágenes puramente decorativas.
- **Prioridad:** P3.

### 13. Imagen social sin formato dedicado

- **Impacto:** Medio para CTR social y enlaces compartidos.
- **Evidencia:** Open Graph utiliza `hero.webp` de 1647×955 (relación aproximada 1,72:1), no un asset diseñado para 1200×630.
- **Recomendación:** crear una imagen OG de 1200×630 con marca, fecha, ubicación y contraste alto; declarar `width`, `height` y `type` en metadata. Crear también imagen específica para `/apply` si se comparte esa URL.
- **Prioridad:** P2.

## Contenido, autoridad y confianza

### 14. Arquitectura demasiado pequeña para crecer orgánicamente

- **Impacto:** Alto.
- **Evidencia:** el sitemap contiene solo la home y `/apply`.
- **Problema:** una sola landing intenta cubrir marca, programa, metodología, requisitos, becas, ubicación y preguntas frecuentes. No existe suficiente superficie para atacar intenciones específicas ni crear clusters internos.
- **Recomendación inicial:** crear páginas sustantivas, no páginas delgadas:
  - `/programa`: metodología, módulos, resultados y agenda.
  - `/admisiones`: requisitos, fechas, selección y compromisos.
  - `/becas`: elegibilidad, cobertura y proceso.
  - `/para-colegios` o `/partners`: propuesta para colegios/empresas.
  - `/sobre-hiveyoung`: organización, equipo, experiencia e impacto.
  - Casos/testimonios con nombre, colegio/rol y evidencia verificable.
- **Prioridad:** P1.

### 15. Señales de confianza incompletas

- **Impacto:** Alto para conversión y Medio-Alto para E-E-A-T.
- **Evidencia:** el sitio recoge datos personales de menores mediante `/apply`, pero no enlaza una política de privacidad, términos, responsable de datos, contacto institucional o condiciones del programa.
- **Recomendación:** publicar y enlazar desde el formulario y footer: Política de Privacidad, Términos/Reglamento, contacto institucional y detalles de tratamiento/retención de datos. Revisar el texto legal con asesoría competente, especialmente por tratarse de menores.
- **Prioridad:** P1.

### 16. Poca evidencia de experiencia e impacto

- **Impacto:** Medio-Alto.
- **Evidencia:** hay logos de aliados, programa y FAQ, pero no se muestran equipo, docentes/mentores, cohortes anteriores, resultados, testimonios verificables ni cobertura externa.
- **Recomendación:** añadir perfiles de organizadores/mentores, cifras de impacto con fuente, testimonios reales, instituciones participantes y enlaces externos verificables. Evitar métricas sin respaldo.
- **Prioridad:** P2.

### 17. Correcciones editoriales

- **Impacto:** Bajo-Medio.
- **Evidencia:** aparecen “Chekpoint” en el programa y una mezcla abundante de español e inglés (“Skills del Futuro”, “leaders, builders y founders”).
- **Recomendación:** corregir “Checkpoint” y definir una guía editorial consistente. Mantener anglicismos solo cuando sean parte consciente de la marca y explicar los términos para audiencia/parents.
- **Prioridad:** P3.

## Plan priorizado

### Primeros 7 días

1. Comprimir/reexportar imágenes grandes y aplicar lazy loading/`next/image`.
2. Corregir el H1 para explicitar “bootcamp para jóvenes”.
3. Convertir o retirar la navegación falsa del footer.
4. Publicar Política de Privacidad y contacto institucional; enlazarlos desde `/apply` y footer.
5. Corregir los 3 errores de lint y las advertencias relacionadas con imágenes.
6. Validar el schema del evento en Rich Results Test.

### Próximos 30 días

1. Separar la home en Server Components e islas interactivas.
2. Crear páginas profundas de Programa, Admisiones y Becas.
3. Crear imagen OG 1200×630 y metadata específica por página.
4. Mejorar schema de evento y coherencia `es-CL`.
5. Configurar Google Search Console y Bing Webmaster Tools; enviar sitemap.

### Próximos 60–90 días

1. Construir un cluster de contenidos según datos reales de Search Console.
2. Publicar testimonios/casos y perfiles de mentores/equipo.
3. Conseguir enlaces desde HiveYoung, UC, aliados, colegios y medios relevantes hacia páginas específicas.
4. Medir CTR, consultas no-branded, páginas indexadas, conversiones a postulación y Core Web Vitals.

## Métricas recomendadas

- Cobertura/indexación de las 2 URLs actuales y de nuevas páginas.
- Impresiones y clics de marca vs. no marca.
- CTR por consulta y página.
- LCP < 2,5 s; INP < 200 ms; CLS < 0,1 en datos de campo.
- Peso transferido inicial en móvil y JavaScript total.
- Conversión orgánica de visita a inicio/finalización de postulación.
- Backlinks y dominios referentes institucionales.

## Limitaciones de esta auditoría

- No se contó con acceso a Google Search Console, Google Analytics ni datos históricos de conversiones.
- PageSpeed Insights no entregó un informe en esta ejecución por límite de cuota de su API; por eso no se inventan puntuaciones Lighthouse. Los problemas de rendimiento aquí se basan en pesos reales de assets, estructura del frontend y comportamiento de carga observado.
- No se realizó análisis competitivo de palabras clave ni backlinks con Ahrefs/Semrush.
